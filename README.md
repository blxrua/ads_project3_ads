# Safe Fruit（安全水果）八版本实现

## 报告

- `report_safe_fruit.tex` / `report_safe_fruit.pdf`：PTA 作业报告

- `tests/`：报告中使用的 12 组手写测试输入，以及运行说明。

## 1. 问题建模

- 水果 = 顶点，一条“不能同吃”的提示 = 一条无向边。
- 能同时拿的水果集合 = 图的**独立集**。
- 目标：独立集大小最大；大小相同时总价格最小。

## 2. 双关键字 → 单关键字

取 `BIGW = 100001`（严格大于最大可能总价 `100 × 1000 = 100000`），令

```
score[v] = BIGW - price[v]
```

对集合 S：

```
总分数 = |S| × BIGW - 总价格
```

因此**总分数越大 ⇔ 个数越多；个数相同时 ⇔ 总价越低**。搜索时只需维护一个 `bestScore`。

## 3. 上界剪枝（精确版）

搜索状态里的 `cand` 表示**与所有已选水果都不冲突**的候选水果集合
（选了 v 之后，`cand & ~adj[v]` 自动把 v 的冲突邻居全部剔除）。
所以上界只统计这些“兼容”水果，而不是全部剩余水果。

在此基础上再做一层收紧——**贪心匹配上界**：

- 在 `cand` 内部按“冲突边”做贪心匹配；
- 一条匹配边两端至多选一个，因此每对最多贡献两者中较大的分数；
- 未匹配的点各贡献自己的分数；
- 求和即为 `cand` 内任意独立集分数的上界。

它一定不小于真实可取值，且比“把 `cand` 全部分数相加”更紧。

> 实测：若只用“剩余所有水果分数相加”（包含与已选冲突的水果），
> 100 个点的路径 / 环会超时；改成上面的精确上界后，所有压力用例都在 0.1 s 内。

## 4. 版本设计：四版本消融与 v5～v8 优化

| 版本 | 文件 | 分支策略 | 分量分解 | 包含步骤 |
|---|---|---|---|---|
| 版本 1 | `v1_steps123.c` | 固定顺序（最小下标） | 否 | 步骤 1、2、3 |
| 版本 2 | `v2_full.c` | 候选集内最大度数 | 是 | 步骤 1、2、3、4、5 |
| 版本 3 | `v3_ablate_step4.c` | 固定顺序（最小下标） | 是 | 步骤 1、2、3、5（消融步骤 4） |
| 版本 4 | `v4_ablate_step5.c` | 候选集内最大度数 | 否 | 步骤 1、2、3、4（消融步骤 5） |
| 版本 5 | `v5_static_degree.c` | 回溯前按初始冲突数降序排一次 | 是 | 步骤 1、2、3、5 + 静态预排序 |
| 版本 6 | `v6_tree_dp.c` | 树分量用树形 DP；有环分量沿用 v2 | 是 | v2 + 树形 DP |
| 版本 7 | `v7_cycle_tree_dp.c` | 检测到候选诱导子图为森林时用树形 DP | 是 | v6 + DFS 中动态森林检测 |
| 版本 8 | `v8_cycle_tree_dp.c` | 按环秩与候选集缩小幅度触发森林检测 | 是 | v7 + 自适应检测时机 |

- **版本 1 → 版本 2**：完整改进的效果。
- **版本 3 = 版本 2 消融步骤 4**：只把分支点换回固定顺序。
- **版本 4 = 版本 2 消融步骤 5**：只去掉连通分量分解。
- **版本 5 = 版本 1 加静态预排序和分量分解**：按初始冲突数从大到小排一次（相同时按输入下标），先拆分原图的连通分量，再在每个分量内沿用这份固定顺序搜索；不重新计算当前度数。
- v1~v5 共用步骤 1~3：分数编码、回溯、精确上界剪枝、孤立水果直接选入。v5 另外启用步骤 5 的连通分量分解。
- 版本 6 检测每个连通分量；若边数等于顶点数减一，就用树形 DP，否则沿用 v2 回溯。
- 版本 7 对有环分量也在回溯过程中检测候选诱导子图。初始环秩小于 3 时，候选点每减少 5 个开始检测；环秩至少 3 时，候选点不多于 15 个时开始检测。若仍有环，则每再减少 5 个点复查；一旦成为森林，就对剩余候选图做树形 DP。
- 版本 8 对每个有环分量单独计算环秩。候选点移除数达到环秩一半（向上取整）后开始检测；若尚未成森林，之后只在一次分支使候选集缩小至少 2 个点时复查。首次检测阈值限制在分量点数以内。

实现上用纯 C（C99），只引入 `<stdio.h>` 和 `<stdint.h>`：候选集合用两个 `uint64_t`
表示位掩码，`mask_add / mask_del / mask_has` 等辅助函数通过指针操作；
邻接表用二维数组 `adjList[MAXM][MAXM]` 加 `deg[]`；排序用手写插入排序。

## 8. full 生成器套件

light 的六个族是“理想形态”，顶点编号也沿着结构排列，容易高估固定顺序分支。
full 套件专门补上这两点：

- **规模**：M = 10, 20, ..., 100；10 个种子；3 种价格分布。
- **规范族**（6 个）：path、cycle、star、tree、sparse100、components，
  每个规模/分布/种子都生成，共 1800 组。
- **机制族**（4 个，M = 20/40/60/80/100）：
  - `groups`：若干互相重叠的小团，模拟“忌口组”；
  - `sbm`：两层社区，叶社区稠密、父社区中等、跨社区稀疏；
  - `coreper`：小核心全连接，其余点挂 1~3 个核心点；
  - `banded`：先连最近邻形成带宽，再补少量长程边。
  共 600 组。
- **特殊**：K10,10 与全孤立点，共 60 组。
- **标签置换**：每个实例都做随机 ID 双射，并打乱水果行、提示行及提示方向；
  结构不变，但“下标顺序”不再携带结构信息。
- **标注**：SCIP，`limits/gap = 0`，与 light 相同。

产物为 `bench/instances_full/`、`bench/manifest_full.json`、
`bench/results_full.csv`、`bench/summary_full.csv`。

观察：

- **v2 是唯一 0 超时的版本**，总时间 30.5 s，约为 v1 的 1/19、v3 的 1/8、
  v4 的 1/6；完成节点总和也最少（49.8 M，v1 为 701.6 M）。
- **步骤 5 仍然是决定性的**。components 在 M=90 时 v1 30/30 超时、v4 21/30
  超时，而 v2/v3 分别只要 0.06/0.04 ms；M=70 时 v1 也有 26/30 超时。
  v4（最大度数但不分解）在 M=90 仍会成片超时，说明**步骤 4 替代不了步骤 5**。
- **步骤 4 在非规则图上收益很大**：tree100 从 298.06 降到 8.25 ms
  （节点 530,621 → 18,268）；sparse100 从 239.55 降到 9.74
  （426,228 → 20,230）；banded100 从 1010.92 降到 162.16
  （2,372,985 → 243,686）；sbm100 从 200.90 降到 4.67（507,088 → 9,130）。
- **core-periphery 是反例**：v2 0.14 ms、v1/v3 0.04 ms，v2 节点数约 2.6 倍。
  图本身容易，最大度数枢轴只增加了扫描开销；但绝对时间仍可忽略。
- **light 的“路径/环上步骤 4 慢 57 倍”是对齐编号的假象**。full 中
  path100 的 v1 从 0.47 ms 涨到 362.56 ms（约 770 倍），cycle100 从
  0.07 ms 涨到 436.61 ms（约 6150 倍），而 v2 只从 27 ms 涨到 135~150 ms
  （约 5 倍）。置换后 v2 在 30/30 个 path100 和 cycle100 实例上都更快，
  节点数为 v1 的 0.283/0.204 倍。也就是说，固定顺序在 light 里“赢”
  主要是因为顶点编号沿结构排列；输入顺序任意时它反而更脆弱。
- **机制族给出不同答案**：重叠团 groups 对 v2/v3 都容易（M=100 为
  0.09/0.11 ms）；层次社区 sbm 与带状 banded 上 v2 明显更好；
  core-periphery 上固定顺序 v1/v3 更好。没有一个枢轴规则在所有形态上占优，
  但 v2 没有灾难性超时，这是提交版选择 v2 的主要理由。

> 生成器仍是受控近似：它能覆盖重叠团、层次社区、核心-边缘、带状等形态，
> 但不能替代真实数据。若有真实用例，直接用同一个 `run.py` 即可复测。

## 10. 复杂度

- 时间：最坏 O(2^M)（M <= 100）；分量分解 + 精确上界后实测搜索量很小。
- 每次上界计算 O(V + E)，V、E <= 100。
- 空间：O(M)。
