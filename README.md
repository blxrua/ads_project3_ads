# Safe Fruit（安全水果）四版本实现

## 1. 问题建模

- 水果 = 顶点，一条“不能同吃”的提示 = 一条无向边。
- 能同时拿的水果集合 = 图的**独立集**。
- 目标：独立集大小最大；大小相同时总价格最小。

## 2. 双关键字 → 单关键字

取 `BIGW = 100001`（严格大于最大可能总价 `100 × 1000 = 100000`），令

```
score[v] = BIGW - price[v]
```

对集合 S：

```
总分数 = |S| × BIGW - 总价格
```

因此**总分数越大 ⇔ 个数越多；个数相同时 ⇔ 总价越低**。搜索时只需维护一个 `bestScore`。

## 3. 上界剪枝（精确版）

搜索状态里的 `cand` 表示**与所有已选水果都不冲突**的候选水果集合
（选了 v 之后，`cand & ~adj[v]` 自动把 v 的冲突邻居全部剔除）。
所以上界只统计这些“兼容”水果，而不是全部剩余水果。

在此基础上再做一层收紧——**贪心匹配上界**：

- 在 `cand` 内部按“冲突边”做贪心匹配；
- 一条匹配边两端至多选一个，因此每对最多贡献两者中较大的分数；
- 未匹配的点各贡献自己的分数；
- 求和即为 `cand` 内任意独立集分数的上界。

它一定不小于真实可取值，且比“把 `cand` 全部分数相加”更紧。

> 实测：若只用“剩余所有水果分数相加”（包含与已选冲突的水果），
> 100 个点的路径 / 环会超时；改成上面的精确上界后，所有压力用例都在 0.1 s 内。

## 4. 四个版本（2 × 2 消融设计）

| 版本 | 文件 | 分支策略 | 分量分解 | 包含步骤 |
|---|---|---|---|---|
| 版本 1 | `v1_steps123.c` | 固定顺序（最小下标） | 否 | 步骤 1、2、3 |
| 版本 2 | `v2_full.c` | 候选集内最大度数 | 是 | 步骤 1、2、3、4、5 |
| 版本 3 | `v3_ablate_step4.c` | 固定顺序（最小下标） | 是 | 步骤 1、2、3、5（消融步骤 4） |
| 版本 4 | `v4_ablate_step5.c` | 候选集内最大度数 | 否 | 步骤 1、2、3、4（消融步骤 5） |

- **版本 1 → 版本 2**：完整改进的效果。
- **版本 3 = 版本 2 消融步骤 4**：只把分支点换回固定顺序。
- **版本 4 = 版本 2 消融步骤 5**：只去掉连通分量分解。
- 四个版本共用步骤 1~3：分数编码、回溯、精确上界剪枝、孤立水果直接选入。

实现上用纯 C（C99），只引入 `<stdio.h>` 和 `<stdint.h>`：候选集合用两个 `uint64_t`
表示位掩码，`mask_add / mask_del / mask_has` 等辅助函数通过指针操作；
邻接表用二维数组 `adjList[MAXM][MAXM]` 加 `deg[]`；排序用手写插入排序。

`test_random.py` 会检查：ID 递增、无重复、都在篮子里、两两不冲突、
总价正确，且（个数，价格）等于暴力最优值。`test_special.py` 还会枚举
全部最优解，确认输出属于其中一种。

benchmark 说明：

- 实例：路径、环、星、随机树、100 边稀疏图、多分量 6 个族 × M=30/60/90/100
  × 3 种价格分布 × 5 个种子；另加 K10,10 和全孤立点。
- 标注：OR-Tools 里的 SCIP，`limits/gap = 0`。默认相对 gap 1e-4 在目标约 1e6 时
  会放过几个价格单位的差，必须关掉。
- 计时：程序内 `QueryPerformanceCounter` 只包住搜索；单次 <10 ms 的实例重复 5 次
  取中位，慢实例只跑 1 次；超过 5 s 直接杀掉，记为 timeout（截断值）。
- 输出：`bench/results_light.csv`（逐实例）、`bench/summary_light.csv`（按族/规模聚合）。

## 7. 实测结果（light，单位 ms，机器相关）

下表是每族 15 个实例的中位数；括号内是该格的最坏值或超时次数。

| 用例 | v1 | v2 | v3 | v4 |
|---|---|---|---|---|
| path100 | 0.47 | 27.1 | 0.47 | 27.1 |
| cycle100 | 0.07 | 27.0 | 0.07 | 27.4 |
| star100 | 0.08 | 0.11 | 0.08 | 0.11 |
| tree90 | 26.8（最坏 2302） | 5.9 | 27.1（最坏 2296） | 5.8 |
| tree100 | 57.2（1 次超时） | 9.3 | 57.0（1 次超时） | 9.1 |
| sparse100，M=90 | 71.1 | 7.3 | 73.2 | 7.3 |
| sparse100，M=100 | 65.2（1 次超时） | 7.6 | 65.6（1 次超时） | 7.6 |
| 多分量，M=30（10 个三角形） | 11.8 | 0.0036 | 0.0026 | 0.37 |
| 多分量，M=60（10 个六边形） | 0.096 | 0.021 | 0.0098 | 1.08 |
| 多分量，M=90（9 个九边形） | >5000（15 次超时） | 0.062 | 0.032 | >5000（15 次超时） |
| 多分量，M=100（10 个十边形） | 0.55 | 0.099 | 0.032 | 8.4 |

观察：

- **步骤 5（分量分解）在多分量图上是决定性的**：10 个三角形从 11.8 ms 降到
  0.003 ms；9 个九边形上 v1/v4 全部超时，v2/v3 只需 0.03~0.06 ms。
- **步骤 4（最大度数分支）分场景**：100 边随机图上把 71 ms 降到 7.3 ms（约 10 倍），
  但在路径/环上从 0.47 ms 涨到 27 ms（约 57 倍）——每个节点都要 O(M²) 选枢轴，
  规则图上选出的分支点也不更好。
- **只加最大度数救不了多分量**：v4 在 M=90 上仍全部超时，M=100 也要 8.4 ms，
  而 v3 只用 0.032 ms。
- v2 综合最稳；v3 在规则图上最快；v1 在随机稀疏图和大分量上会指数爆炸。

## 8. full 生成器套件

light 的六个族是“理想形态”，顶点编号也沿着结构排列，容易高估固定顺序分支。
full 套件专门补上这两点：

- **规模**：M = 10, 20, ..., 100；10 个种子；3 种价格分布。
- **规范族**（6 个）：path、cycle、star、tree、sparse100、components，
  每个规模/分布/种子都生成，共 1800 组。
- **机制族**（4 个，M = 20/40/60/80/100）：
  - `groups`：若干互相重叠的小团，模拟“忌口组”；
  - `sbm`：两层社区，叶社区稠密、父社区中等、跨社区稀疏；
  - `coreper`：小核心全连接，其余点挂 1~3 个核心点；
  - `banded`：先连最近邻形成带宽，再补少量长程边。
  共 600 组。
- **特殊**：K10,10 与全孤立点，共 60 组。
- **标签置换**：每个实例都做随机 ID 双射，并打乱水果行、提示行及提示方向；
  结构不变，但“下标顺序”不再携带结构信息。
- **标注**：SCIP，`limits/gap = 0`，与 light 相同。

产物为 `bench/instances_full/`、`bench/manifest_full.json`、
`bench/results_full.csv`、`bench/summary_full.csv`。

## 9. 复杂度

- 时间：最坏 O(2^M)（M <= 100）；分量分解 + 精确上界后实测搜索量很小。
- 每次上界计算 O(V + E)，V、E <= 100。
- 空间：O(M)。
